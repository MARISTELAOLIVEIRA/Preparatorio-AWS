C1–C5 · conceitos

Como a AWS avalia uma arquitetura

C1

Os seis pilares do Well-Architected

O AWS Well-Architected Framework reúne as boas práticas da AWS e um jeito de avaliar uma arquitetura. Ele tem seis pilares, e cada problema do caso cai num deles.

PilarA pergunta que ele fazProblema do caso
Excelência operacionaloperational excellenceVocê roda bem, enxerga o que acontece e melhora sempre os processos?3: ninguém sabe quem mudou a configuração.
SegurançasecurityOs dados, os sistemas e os acessos estão protegidos?5: a cópia do banco sem criptografia.
ConfiabilidadereliabilityO sistema faz o que deve, quando deve, e se recupera de falhas?1: o site caiu quando uma máquina travou.
Eficiência de desempenhoperformance efficiencyVocê usa os recursos certos e continua eficiente quando a demanda muda?4: a página lenta com muita gente.
Otimização de custoscost optimizationVocê entrega o resultado pelo menor preço?2: a conta dobrou sem explicação.
SustentabilidadesustainabilityVocê reduz o consumo de energia e usa só o necessário?6: máquinas grandes ligadas à toa a noite toda.

Fonte: AWS Well-Architected Framework: definitions, consultado em 04/11/2026.

A AWS Well-Architected Tool, no console, faz as perguntas de cada pilar e mostra os riscos da sua arquitetura.

C2

Projetar para falhar: alta disponibilidade

Na nuvem, a ideia é planejar como se tudo fosse falhar um dia, e montar o sistema para continuar no ar mesmo assim. Você já viu as peças:

  • Nada de ponto único de falha: nenhuma peça sozinha pode derrubar tudo.
  • Várias zonas de disponibilidade (aula 3), com o banco em Multi-AZ (aula 8).
  • Crescer e diminuir sozinho conforme a demanda, com o Auto Scaling (aula 10).
  • Automatizar em vez de fazer à mão: menos erro humano.

Na Ingresso Candango: o site que caiu quando uma máquina travou (problema 1) tinha uma máquina só. Com duas ou mais, em zonas diferentes, uma falha não derruba o site.

C3

Fonte: AWS Trusted Advisor, consultado em 04/11/2026.

C4

O CAF: a mudança é também de pessoas

Ir para a nuvem não é só técnica. O AWS Cloud Adoption Framework (CAF) organiza a mudança em seis perspectivas:

PerspectivaCuida de
NegóciosbusinessQue a nuvem traga resultado para o negócio.
PessoaspeopleA cultura, a liderança e a capacitação da equipe.
GovernançagovernanceOrganizar as iniciativas, com os benefícios no máximo e os riscos no mínimo.
PlataformaplatformA base técnica, escalável e híbrida, e a modernização dos sistemas.
SegurançasecurityA confidencialidade, a integridade e a disponibilidade dos dados.
OperaçõesoperationsQue os serviços funcionem no nível que o negócio precisa.

E os resultados que o CAF promete, segundo o guia da prova: menos risco para o negócio, melhor desempenho ambiental, social e de governança (ESG), mais receita e mais eficiência operacional.

Fontes: AWS, Overview of the AWS CAF e guia da CLF-C02, Domínio 1, consultados em 04/11/2026.

C5

Os 7 Rs da migração

Cada sistema antigo da rede de casas de show pode seguir um caminho diferente:

EstratégiaO que fazExemplo
DesativarretireDesliga o que ninguém usa mais.O sistema de fax de 2010.
ManterretainDeixa onde está, por enquanto.Um sistema preso a uma máquina especial do palco.
Rehospedarrehost, lift and shiftLeva para a AWS do jeito que está, sem mudar nada.O servidor do site vira uma instância do EC2.
RealocarrelocateMove a plataforma inteira para a versão dela na nuvem, sem mudar a aplicação.Muitas máquinas virtuais de uma vez.
RecomprarrepurchaseTroca por um produto novo, quase sempre um SaaS.O sistema de RH antigo vira um SaaS de RH.
ReplataformarreplatformLeva com alguns ajustes, para aproveitar a nuvem.O banco SQL Server vai para o RDS.
Refatorarrefactor, re-architectRedesenha para a nuvem. É o mais complexo e caro.O sistema de vendas vira contêineres e Lambda.

Fonte: AWS Prescriptive Guidance, migration strategies, consultado em 04/11/2026.

Agora planeje a mudança da rede de casas de show: um R para cada sistema. Pense numa mudança de casa.

  3. 🌐 O servidor do sitelevar rápido, sem mudar nada

  4. 🖥️ Dezenas de máquinas virtuaisa plataforma inteira, de uma vez, sem mexer nos sistemas

  5. 🗄️ O banco SQL Serverlevar, mas parar de cuidar do banco

  6. 👥 O sistema de RH antigoexiste pronto como SaaS

P1 · pegadinha de prova

Pilares parecidos, perguntas diferentes

Três pares de pilares se confundem. A pista está no problema que a questão descreve:

Se a questão fala em…ÉE não
Recuperar de falhas, continuar no ar.ConfiabilidadeEficiência de desempenho, que é sobre usar os recursos certos.
Processos, mudanças pequenas e frequentes, aprender com os erros.Excelência operacionalConfiabilidade.
Energia, impacto ambiental, usar menos recursos.SustentabilidadeOtimização de custos, que é sobre o preço.
⏸Pausa aquiO banco SQL Server vai para o RDS, sem reescrever a aplicação. É rehost ou replatform?ver a resposta

Replatform: leva com um ajuste (trocar para um banco gerenciado). Rehost seria levar o banco do jeito que está, numa máquina do EC2.

E na migração: "sem mudar nada" é rehost; "com alguns ajustes, como ir para um banco gerenciado" é replatform; "redesenhar para a nuvem" é refactor. Trocar por um SaaS é repurchase.

T1

Qual pilar?

Agora é com você:

  1. O sistema precisa se recuperar sozinho quando uma instância falha.
  2. Desligar à noite as máquinas de teste para a conta cair.
  3. Criptografar os dados e dar a cada pessoa só o acesso necessário.
  4. Fazer mudanças pequenas e frequentes e registrar o que aprendeu com cada erro.
  5. Trocar o tipo de instância por um que atende melhor o volume de acessos.
  6. Reduzir o consumo de energia usando só os recursos necessários.
T2

Qual R da migração?

Agora é com você:

  1. Copiar o servidor para o EC2 do jeito que está, o mais rápido possível.
  2. Levar o sistema e trocar o banco instalado na máquina pelo RDS.
  3. Reescrever o sistema em microsserviços com contêineres e Lambda.
  4. Trocar o sistema de e-mail próprio por um serviço de e-mail pronto, pago por mês.
  5. Desligar um relatório que ninguém abre há dois anos.
  6. Deixar no prédio um sistema que, por regra, não pode sair de lá agora.
T3

Qual perspectiva do CAF?

Agora é com você:

  1. Treinar a equipe e preparar a liderança para a mudança.
  2. Mostrar ao diretor financeiro que a nuvem vai aumentar a receita.
  3. Desenhar a base técnica, com rede, contas e a nuvem híbrida.
  4. Controlar os riscos e os gastos de todos os projetos de nuvem.
  5. Garantir que os serviços funcionem no nível combinado com o negócio.
  6. Proteger a confidencialidade e a integridade dos dados dos clientes.
